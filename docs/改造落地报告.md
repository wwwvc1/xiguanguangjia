## 2. Phase 1:结构性性能修复

### 2.1 同步连接池(收益最直接)

`get_sync_connection()` 原来每次调用 = 一次 TCP 握手 + MySQL 认证,而它被 **25+ 处请求热路径**使用。

现在:`core/database.py` 内置一个线程安全的小池(`SyncConnectionPool`),
**返回值的 `close()` 被重写为「归还」**,所以旧代码
`conn = get_connection(); try: ... finally: conn.close()` 一行都不用改。
归还时 `rollback()` 清掉未提交事务;借出前 `ping(reconnect=True)` 救回被 MySQL 断掉的长连接。

### 2.2 一个隐蔽但严重的老 bug:REPEATABLE READ 冻结快照 🔴

排查过程中发现 `POST /todos` 会**间歇性 500**(约 1/3 概率),根本原因:

> MySQL 默认隔离级别是 REPEATABLE READ,事务快照在**首条 SELECT** 时建立。
> 连接池里的连接如果只做过读、从不 `commit`/`rollback`,这条连接会永久停留在旧快照上 ——
> 之后它读到「刚被别的连接插入的行」时返回 `None`。
> 现象:INSERT 成功,紧接着的 SELECT 拿不到这一行。

这在改造前就存在(只是原来的池小、读写混用把它掩盖了),改造后池变大立刻暴露。

修复:`core/database.py` 建池时 `autocommit=True`,每条语句各自成为事务;
需要原子性的多语句显式用 `async with transaction()`(内部 `begin()` + commit/rollback)。

### 2.3 索引(实测数据)

新增 6 个复合索引,脚本化幂等应用(`scripts/apply_perf_indexes.py`):

| 表 | 索引 | 服务的查询 |
|---|---|---|
| todos | `(user_id, done, due_date)` | 首页/待办页按天过滤 |
| todos | `(user_id, done, created_at)` | 无日期过滤时的排序 |
| transactions | `(user_id, time)` | 日报/月报/60 天范围扫描 |
| transactions | `(user_id, type, time)` | 支出按天聚合、近 7 天汇总 |
| goals | `(user_id, done)` | 成就 metric |
| reminders | `(user_id, enabled, time)` | 成就 metric |

**基准测试结果**(3 万行合成数据,`scripts/bench_queries.py`,跑完自动清理):

```
[1] todos 按天过滤
    A 原查询 + 无新索引     :  47.42 ms
    B 原查询 + 新索引       :   0.46 ms   (103x)
    C UNION ALL + 新索引    :   0.57 ms   (84x)

[2] transactions 按月聚合
    A YEAR()/MONTH() + 无索引 : 108.74 ms
    B YEAR()/MONTH() + 新索引 :  45.64 ms   (2.4x)
    C 时间区间 + 新索引       :   9.58 ms   (11.3x)
```

> **一个被数据推翻的假设**:我最初的方案说「`due_date = ? OR due_date IS NULL` 会让索引失效,
> 要改写成 UNION ALL」。实测在复合索引下 OR 反而更快(0.46 vs 0.57 ms,MySQL 会做 index merge)。
> 所以最终**保留了最简洁的 OR 写法**,收益全部来自索引本身。代码注释里记了这段。
>
> 而 `transactions` 的 `YEAR()/MONTH()` 确实是函数包裹导致的部分失效:只加索引 2.4x,
> 索引 + 改写成半开区间才有 11.3x —— **两者必须同时做**。

### 2.4 成就引擎:移出热路径

改造前:勾一个待办 → `PUT /api/todos/{id}` → 同步跑 `check_and_unlock`,
遍历 12 条定义 ×(查已解锁 + 算 metric),再算上 1 次新建连接。

改造后:

1. 写请求只 `cache.abump(user, "todo")` + 把评估丢进 `BackgroundTasks`,**响应不等它**;
2. 评估按 metric 去重(12 条定义通常只对应 7 个 metric);
3. 每个 metric 结果按「域版本号」缓存 300s;
4. 用户打开成就页时再兜一次底(`list_available(sync=True)`),所以**体验上等价于实时**;
5. `list_unlocked` 的 N+1(每条成就反查 icon)改成一次 `LEFT JOIN`。

实测:12 条定义全量评估 78.74 ms → 去重后 66.74 ms;
但关键是**这 70 ms 不再挂在用户的写请求上**,缓存命中后趋近 0。

### 2.5 首页 7 请求 → 1 请求

新增 `GET /api/dashboard?date=YYYY-MM-DD`:
服务端 `asyncio.gather` 并发跑 5 条轻查询,整包缓存 60s。

前端 `pages/index/index.js`:

- 优先走 `/dashboard`;
- **失败自动回退**到原来的 6 请求路径(后端没重启也能用)。

实测:首次 14–27 ms → 二次 4–5 ms(缓存命中)。

## 3. Redis 接入

### 3.1 设计原则

**Redis 是加速层,不是正确性依赖。** 三条硬性约束:

1. `socket_timeout = 0.2s` —— Redis 一卡,不能拖住请求;
2. **熔断** —— 连续失败 5 次后短路 15s,期间连网络都不碰(否则每个请求白付一次超时);
3. **降级** —— 任何异常都返回 `None` 让业务回源 MySQL;`REDIS_ENABLED=false` 可整体关闭。

### 3.2 后端双实现

原计划用官方 `redis` 包,但这台机器**出网被拦**(pypi / 清华镜像都连不上),装不了。
为了让缓存层不至于变成死代码,写了 `core/mini_redis.py`:纯标准库的 RESP2 客户端,
覆盖项目实际用到的命令(`PING/GET/SET(NX,EX)/EXPIRE/INCRBY/MGET/DEL` + pipeline)+ 连接池。

`core/redis_client.py` 启动时自动选择:

```
官方 redis 包可用 → redis-py(支持集群/哨兵/异步)
否则            → mini_redis(标准库实现)
```

两者方法签名一致,上层 `cache.py` 完全无感。日志会打印当前后端:

```
INFO core.redis: Redis 后端: mini (127.0.0.1:6379/0)
```

> 等能装官方包时,`pip install redis`,重启即自动切换,无需改代码。

### 3.2.1 本地 Redis 实测环境(已跑通)

| 项 | 值 |
|---|---|

| 端口 | `127.0.0.1:6379` |
| 后端选择 | `mini`(官方 redis 包装不上,走内置实现) |

```

```

> **不需要为这个版本改任何代码。**

#### 但这台实例有两处建议调整

诊断时看到:

```
maxmemory        : 0        ← 无上限
maxmemory-policy : noeviction
save             : 3600 1 300 100 60 10000
```

1. `maxmemory = 0` 表示不限制 —— 缓存会一直长,直到 Windows 内存告急;
2. 如果只把 maxmemory 设成有限值而**保持 noeviction**,内存满后 `SET` 会返回
   `OOM command not allowed`,触发本项目熔断反复开关(缓存时有时无)。
   所以 **maxmemory 与 policy 必须一起改**。

推荐(运行时生效):

```powershell
redis-cli CONFIG SET maxmemory 256mb
redis-cli CONFIG SET maxmemory-policy allkeys-lru
# 纯缓存不需要落盘,关掉 RDB 快照可少一半磁盘 IO(可选)
redis-cli CONFIG SET save ""
```

`CONFIG SET` 重启即失效;要长期生效,把上面三行写进 `redis.windows.conf`
(`save ""` 那一行写成 `save ""` 或者删掉所有 `save` 行)。

> Redis 5.0 上游已 EOL。本地开发无所谓;真要上生产/多 worker,
> 建议直接换 Redis 7 的 Docker 镜像。

### 3.3 版本号失效(按你的选择实现)

```
ver:{uid}:todo     ← 任何 todos 写操作 +1
ver:{uid}:tx       ← 任何 transactions 写操作 +1
...

读:缓存 payload 里存一份写入时的版本快照 {todo: 12, tx: 8}
    当前版本对不上 → 当未命中,回源
```

写方**不需要知道**有多少派生 key,新增缓存永远不会漏失效。TTL 再兜一道底。

已验证:写 todo 后 dashboard 缓存立刻失效(`completed_count` 从 0 变 1)。
settings 变更后 `dashboard.layout` 同步更新。

## 6.1 修复:AI 生成的数据首页看不到

**现象**:在 AI 聊天里让 agent 加一条待办,数据库写成功了,回首页刷新不出来。

**根因是两层,缺一不可修**:

1. **后端**:AI 工具直接操作数据库,完全不经过 routers,**从来没有调用 `cache.abump`**。
   于是 `hb:dash:{uid}:{date}` 在 60 秒 TTL 内一直是旧值。
   (`goals.py` / `reminders.py` 的写操作也有同一个漏洞。)
2. **前端**:`pages/ai/ai.js` 收到 `done` 事件后**没有** `app.bumpDataVersion()`,
   而 `pages/index/index.js` 的 onShow 是靠 `dataVersion` 变化来决定要不要重新拉数据的
   —— 版本号没变,它连请求都不会发。
   (`ai-create.js` 有这个调用,所以从「AI 智能创建」进去是对的,从「AI 聊天」进去就不对。)
